## CPU แปลง Assembly เป็นสัญญาณควบคุมอย่างไร?

มนุษย์อ่าน `lw $t0, 12($s1)` ได้ แต่ CPU อ่านข้อความ `lw` หรือชื่อ `$s1` โดยตรงไม่ได้ คำสั่งถูกเก็บใน Memory เป็น Machine Code 32-bit แล้ว Instruction Decoder จึงแยก Field เพื่อเลือก Control Signals และเส้นทางข้อมูล

### รูปแบบคำสั่ง MIPS

ทั้ง R-type, I-type และ J-type ยาว 32-bit เท่ากัน แต่แบ่ง Field คนละแบบ เลือกตัวอย่างเพื่อดูตำแหน่งของ Field

<InstructionFormatExplorer client:load />

ใน `lw $t0, 12($s1)`, `rs=10001` คือ `$s1`, `rt=01000` คือ `$t0` และ Immediate `12` อยู่ใน 16-bit สุดท้าย Register มี 32 ตัวจึงใช้ Field 5-bit ระบุหมายเลขได้ครบ 0–31 ส่วน `rt` ของ `sw` เป็น Register ต้นทางที่นำข้อมูลไปเก็บใน Memory

### Address ของ Memory และ PC+4

Memory แบบ byte-addressed ให้ Address หนึ่งตำแหน่งต่อข้อมูล 1 byte (8-bit) ส่วน MIPS Instruction ใช้ 32-bit หรือ 4 bytes จึงเริ่มคำสั่งถัดไปห่างออกไป 4 Address

  </div>

### Sign Extension ของ Immediate

I-type มี Immediate 16-bit แต่ ALU ในตัวอย่างทำงานกับข้อมูล 32-bit จึงขยายโดยคัดลอกบิตเครื่องหมาย (บิตซ้ายสุด) ไปทางซ้าย

<div className="extension-example" role="group" aria-label="Sign extension ของเลข -4 จาก 16 บิตเป็น 32 บิต">
  <div><small>16-bit Immediate · −4</small><code>1111 1111 1111 1100</code></div>
  <span aria-hidden="true">→</span>
  <div><small>32-bit Operand · −4</small><code>1111 1111 1111 1111 1111 1111 1111 1100</code></div>
</div>

ถ้าบิตเครื่องหมายเป็น `0` จะเติม `0` เช่น Immediate `+12` กลายเป็น `0000 0000 0000 0000 0000 0000 0000 1100` ส่วน `lw` และ `sw` ใช้ค่านี้เป็น Offset บวกหรือลบได้ สำหรับ `beq` ให้ Sign-extend ก่อนเลื่อนซ้าย 2 บิตเพื่อหา Branch Target

## SLT ใช้ Sign กับ Overflow พร้อมกัน

Signed SLT ต้องคำนึงถึง Overflow ของการลบด้วย โดยบิตผลเปรียบเทียบคำนวณจาก `Sign(A−B) XOR Overflow`

<div className="two-paths slt-overflow-cases" aria-label="ตัวอย่าง Signed comparison ที่เกิด Overflow">
  <div>
    <b>A=7, B=−8</b>
    <code>A−B=15 → เก็บ 1111</code>
    <span>Sign=1, Overflow=1</span>
    <strong>Set=1 XOR 1=0 · 7 &lt; −8 เป็น False</strong>
  </div>
  <div>
    <b>A=−8, B=7</b>
    <code>A−B=−15 → เก็บ 0001</code>
    <span>Sign=0, Overflow=1</span>
    <strong>Set=0 XOR 1=1 · −8 &lt; 7 เป็น True</strong>
  </div>
</div>

ตัวเลขนี้ใช้ 4-bit เพื่อให้เห็น Overflow ชัด ๆ หลักการเดียวกันใช้กับ ALU 32-bit โดยพิจารณา Sign และ Overflow จากผลลบจริง

## หา Branch Offset และ Jump Address

`beq` เก็บ Offset เป็นจำนวนคำสั่ง ไม่ใช่จำนวน Byte จึงคูณ 4 ก่อนบวกกับ `PC+4`

<MathBlock tex={"Target=(PC+4)+(SignExt(offset)\\ll2)"} />

ย้อนหา Offset ได้ด้วย `offset = (Target − (PC+4)) / 4` ตัวอย่าง `PC=0x00400020` และ `Target=0x00400014`:

<div className="branch-offset-card" role="group" aria-label="ตัวอย่างการหา Branch Offset">
  <div><small>PC ของ beq</small><code>0x00400020</code></div>
  <div><small>PC+4</small><code>0x00400024</code></div>
  <div><small>Target</small><code>0x00400014</code></div>
  <strong>Offset = (0x00400014 − 0x00400024) / 4 = −4 <span>· Immediate 16-bit = 0xFFFC</span></strong>
</div>

ใน Multicycle State 1, Fetch เพิ่ม `PC` เป็น `PC+4` ไปแล้ว วงจรจึงใช้ค่า PC ปัจจุบันบวก `SignExt(offset) << 2` ได้ตามสูตร

สำหรับ `j`, 4 บิตบนของ Jump Address มาจาก `(PC+4)[31:28]` เมื่อเขียนใน State หลัง Fetch ที่ `PC` เพิ่มแล้ว จะเห็นเป็น `PC[31:28]`

### เมื่อโจทย์เปลี่ยน ให้ตาม Data Flow

<div className="variation-grid" aria-label="เปรียบเทียบการเปลี่ยนโจทย์ Multicycle">
  <div><b>`lw` → `sw`</b><span>State 1 ยังหา Address ด้วย `rs + offset`; State 2 เปลี่ยนจากอ่าน Memory/เขียน Register เป็นเขียน Memory</span></div>

  <div><b>Branch Taken → Not Taken</b><span>คำนวณ Target แยกไว้เหมือนเดิม; เมื่อ `Zero=0` จะคง `PC+4` ไว้</span></div>
</div>

สำหรับ `srl` (logical right shift) บิตที่เลื่อนเข้ามาทางซ้ายเป็น `0`; `sra` (arithmetic right shift) จึงคัดลอกบิตเครื่องหมายแทน

## Pipeline: จำนวน Clock, Stall และ Memory

สำหรับ Pipeline 5 Stages แบบไม่มี Stall, `N` instructions ใช้ `N+4` Clock จน Instruction สุดท้ายเสร็จ ถ้ามี Stall ให้บวก Clock ที่หยุดรอเข้าไป

<MathBlock tex={"\\boxed{Cycles=N+4+StallCycles}"} />

ตัวอย่าง 10 Instructions และมี Load-Use Stall 1 Clock ใช้ `10+4+1=15 Cycles` ถ้า clock rate เท่ากับ `1 GHz` (คาบ `1 ns`) จะใช้เวลา `15 ns`

<div className="memory-level-flow" role="group" aria-label="Memory hierarchy จาก CPU ไป Cache และ Main Memory">
  <div><small>เร็วที่สุด</small><strong>CPU</strong><span>ทำงานกับข้อมูล</span></div>
  <span aria-hidden="true">→</span>
  <div><small>ใกล้ CPU</small><strong>Cache</strong><span>เล็กและเร็วกว่า RAM</span></div>
  <span aria-hidden="true">→</span>
  <div><small>ความจุมากกว่า</small><strong>Main Memory</strong><span>ใหญ่กว่าแต่ช้ากว่า</span></div>
</div>

Cache Hit ช่วยลดเวลารอเข้าถึง Memory แต่ไม่ได้ทำให้ข้อมูลจาก `lw` พร้อมก่อนเวลา Dependency ระหว่าง `lw` กับคำสั่งถัดไปที่ใช้ผลทันทีจึงยังต้อง Stall ตามจังหวะของ Pipeline แล้วค่อย Forward ข้อมูล

## Load-Use Stall ค้างอะไร และส่ง Bubble ตรงไหน?

เมื่อ `lw` อยู่ MEM และคำสั่งถัดไปต้องรอข้อมูล Hazard Detection จะหยุดคำสั่งใหม่ชั่วคราวโดยไม่ลบ Control ของ `lw` ที่เดินทางอยู่

<div className="stall-action-grid" role="group" aria-label="การควบคุม Pipeline เมื่อ Stall">
  <div><small>PC</small><strong>Hold</strong><span>ยังไม่ Fetch คำสั่งใหม่</span></div>
  <div><small>IF/ID</small><strong>Hold</strong><span>เก็บ Instruction ที่กำลังรอไว้</span></div>
  <div><small>ID/EX</small><strong>Bubble</strong><span>ส่ง Control ที่ไม่มีผลเข้า EX</span></div>
</div>

Control ของ `lw` ที่เดินทางอยู่ใน EX/MEM ยังทำงานของมันต่อ ขณะที่ Main Control ใน ID สร้างค่าชุดใหม่สำหรับ Instruction ที่รออยู่

</section>
